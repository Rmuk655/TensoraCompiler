# V0.3 research pitch: verified ragged tensor compilation with sub-polyhedral scheduling

One page. A research direction for V0.3, aligned with Prof. R.
Upadrasta's polyhedral + DL work. Scoped honestly against the spike
results in this directory. Final scope depends on what the professor
wants.

## Problem

Ragged (variable-length) tensor programs waste memory and compute when
run on padded dense tensors. The spike here confirms the waste is large
(~10-14x memory on a skewed batch; padded attention OOMs on a 4 GB GPU
where ragged fits). But it also shows PyTorch's own `NestedTensor`
already captures this for the **mainstream** inference path (attention,
normalization, FFN, ragged pooling). So the open problem is not "support
ragged tensors." It is:

- ragged ops that `NestedTensor` does **not** cover (for example `cumsum`
  over the sequence dim, positional indexing on the jagged dim, and
  custom fused regions with such ops); and
- ragged code generation for targets where library kernels are weak or
  absent (CPU, edge devices, or new GPU kernels), where a compiler must
  *generate* the ragged schedule, not call a pre-tuned one.

## Why it is novel

Two ideas combine that are not combined elsewhere:

1. **Verified ragged contracts.** Tensora statically proves a ragged
   axis is used safely — every reduction is over the true per-sequence
   length, never over padding. This turns a silent correctness/efficiency
   bug into a compile-time guarantee. No mainstream framework verifies
   this; PyTorch handles it dynamically, per op.
2. **Sub-polyhedral scheduling of the verified ragged program.** The
   proven ragged shape defines a non-rectangular iteration space.
   Scheduling that space is exactly a polyhedral problem, and the
   professor's sub-polyhedral (UTVPI two-variable-per-inequality) work
   gives a fast, tractable scheduler for it (POPL 2013; IMPACT 2011).
   CoRa (MLSys 2022) showed ragged codegen can be competitive; the novel
   part here is driving it from a *verified* contract.

Prior art to cite, not reinvent: CoRa (ragged codegen), PolyDL
(polyhedral for DL primitives), the professor's sub-polyhedral
scheduling, and `torch.nested` (the baseline to beat, honestly).

## What already exists in v0.1

- A working frontend → typed graph → MLIR/`linalg` → LLVM pipeline.
- Statically verified named-axis contracts and a bounded dimension
  solver (`DimSolver`) — the base a ragged-axis contract extends.
- MLIR lowering, so the polyhedral work plugs into MLIR's own affine
  tooling rather than a new scheduler from scratch.

What is missing and is the research work: the ragged axis kind in the
type system, its ragged-safety verification, and the sub-polyhedral
scheduling pass over the ragged MLIR.

## The concrete first experiment

1. Pick one ragged op `NestedTensor` does not cover (for example a
   sequence `cumsum`, or a custom fused region containing one).
2. Baselines: stock PyTorch (padded fallback), and the best
   `NestedTensor` path (which will fall back to padding at the
   unsupported op).
3. Tensora: verify the ragged contract, schedule the ragged iteration
   space (sub-polyhedral), generate the kernel.
4. Measure, in order: floating-point operation count, peak memory, wall
   time; on GPU (via MLIR's GPU path) and on a real edge device.
5. Report against both baselines. The claim stands only if Tensora beats
   the fallback PyTorch actually takes for that op.

## Where the professor's work plugs in

- **Sub-polyhedral scheduling** is the scheduler for the ragged
  iteration space (his POPL 2013 / IMPACT 2011 work applied directly).
- **PolyDL** is the closest prior art for polyhedral DL codegen, and a
  point of comparison.
- If he prefers the ML-for-compilers line (IR2VEC, POSET-RL), a variant
  question fits too: can verified semantic contracts improve a learned
  scheduling or phase-ordering policy over raw IR features? This reuses
  the same verified-contract asset, aimed at his other main line.

## Honest risk

For mainstream inference, `torch.nested` already wins, so this must
target the un-covered ops and weak-kernel targets, or the verification
guarantee itself. Run the first experiment before committing — if the
uncovered cases turn out to be rare or cheap, the direction is
verification, not codegen speed.
