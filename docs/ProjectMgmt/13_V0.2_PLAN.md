# Tensora V0.2 Plan

Full plan for V0.2. Short summary and links: roadmap doc
([11_OPEN_SOURCE_AND_RESEARCH_ROADMAP.md](11_OPEN_SOURCE_AND_RESEARCH_ROADMAP.md),
Section 2).

## Goal

Take an already-trained PyTorch model. Make it use less memory and run
faster. Small code change, no rewrite, no retrain. The user adds one
call where Tensora helps most. The rest stays normal PyTorch.

## MVP claim (the one thing V0.2 must prove)

On a real batch with skewed sequence lengths, Tensora makes a PyTorch
model do **fewer floating-point operations** than stock PyTorch, while
**each remaining operation still runs on a hand-tuned kernel**.

- Fewer ops: Tensora verifies a ragged contract and avoids padding.
- Same per-op speed: Tensora calls existing tuned kernels, it does not
  replace them.
- Net: less work times same per-op speed → faster and smaller.

This is measurable. It does not depend on Tensora writing a fast kernel.

## Delivery form: a PyTorch pass, not a language rewrite

The user never writes Tensora syntax. Tensora is inserted into PyTorch
as one custom op (`torch.library.custom_op()`), or later as a
`torch.compile` graph pass. See
[roadmap doc §9.3](11_OPEN_SOURCE_AND_RESEARCH_ROADMAP.md#93-integration-options-ranked-by-realism)
(option 1a) and
[§9.3a](11_OPEN_SOURCE_AND_RESEARCH_ROADMAP.md#93a-the-tensor-abi-boundary-granularity-and-ownership).
The open question of whether this belongs as a language at all, versus
purely as a PyTorch pass, is in
[roadmap doc §9.7](11_OPEN_SOURCE_AND_RESEARCH_ROADMAP.md#97-be-critical-language-vs-a-pytorch-pass).

## 1. Operator gap for BERT-style models

Three groups. Do them only as a real goal needs them.

- **Group A (small, do first):** `gelu`, `layernorm`, `rename`. Gives one
  full Transformer layer. See
  [roadmap doc §8.9a](11_OPEN_SOURCE_AND_RESEARCH_ROADMAP.md#89a-transformer-layer-completeness-tier--open-source-future).
- **Group B (bigger):** integer element type + `gather` (token
  embeddings), `sin`/`cos`, `avgpool`. See
  [roadmap doc §8.9](11_OPEN_SOURCE_AND_RESEARCH_ROADMAP.md#89-integer-tensor--gather-tier-the-llm-input-path--open-source-future).
- **Group C (biggest):** the ragged axis (pillar 3). Needs a feasibility
  spike first.

**Blocker for Group C, found in the code.** Tensora lowers a symbolic
axis to a dynamic MLIR type, but does not pass the real size to each new
tensor it builds. So a symbolic-shape run fails, and the driver blocks
it today. This is `LOW-005` in
[TEST_MATRIX.md](../testing/TEST_MATRIX.md). A ragged axis is a stronger
form of the same problem. Fix `LOW-005` first.

## 2. PyTorch interop

Tensora's job: verify the region's contract (axis roles, shape
equalities, ragged lengths), then pick how the math runs. Three choices,
best first:

| Choice | What it does | Speed | Memory win | GPU today |
|---|---|---|---|---|
| 1 | Call an existing ragged-aware kernel (`flash_attn_varlen_func`, PyTorch `NestedTensor`, vLLM PagedAttention) | hand-tuned | yes | yes |
| 2 | Tensora compiles the region itself | not hand-tuned | yes | no (CPU-only) |
| 3 | Call an existing padded op (`scaled_dot_product_attention`) | hand-tuned | no | yes |

For the ragged case study, choice 1 is the target. Choice 3 keeps kernel
speed but throws away the memory win. Choice 2 is the fallback when no
ragged kernel matches.

**Dispatch stage and transfer cost.** Choices 1 and 3 happen in the
runtime bridge, not in lowering — the kernel is a callable, not an IR
sink. Choice 1 has no GPU/CPU transfer cost: data stays on the GPU,
Tensora only builds a small sequence-length array. The transfer cost
applies to choice 2 only.

**Why Tensora, not just PyTorch `NestedTensor`.** For an op
`NestedTensor` already covers, Tensora adds static verification, not new
capability. The real win is a custom fused region no `NestedTensor` path
covers (see §3). Be honest in the demo.

**Autograd safety.** Tensora is inference-only (see
[README.md](../../README.md)). The custom op must register as
non-differentiable, or fail loudly under `requires_grad`. Otherwise it
can silently break backprop in a model that is later trained.

**CPU-only (choice 2 only).** Tensora compiles CPU code only today. A
GPU tensor would need a CPU round-trip, which kills the no-copy benefit.
Choices 1 and 3 already run on GPU, because they call an existing GPU
kernel.

## 3. Ragged-tensor performance win

**Padding waste.** PyTorch pads every sequence to the batch max. Batch of
16 sequences, one at 4096 tokens, rest near 16–32: PyTorch allocates
16 × 4096 = 65,536 slots for ~4,160 real tokens (~15.75× waste).
Attention cost is ~n² per sequence, so a short sequence padded to 4096
pays 4096² instead of its own length squared. Wasted compute is worse
than wasted memory.

**Ragged axis.** A new axis kind: one real length per batch element,
verified at compile time. See
[roadmap doc §8.11](11_OPEN_SOURCE_AND_RESEARCH_ROADMAP.md#811-ragged--variable-length-axes)
and
[§4.F](11_OPEN_SOURCE_AND_RESEARCH_ROADMAP.md#f-ragged--variable-length-axis-optimization).
Prior art: the CoRa compiler (MLSys 2022).

**The experiment.** Region: ragged attention → custom normalization →
projection → elementwise, over lengths such as [8, 16, 32, 512].

- Baseline A (honest): stock PyTorch. If it must pad this region, it
  computes ~4 × 512² attention positions plus padded intermediates.
- Baseline B (fair): the best PyTorch `NestedTensor` path for the same
  region, if one exists.
- Tensora: verify `seq = ragged(length[batch])`, process
  8² + 16² + 32² + 512² positions, fuse the trailing ops without
  materializing padded intermediates.
- Measure, in order: floating-point operation count, then peak memory,
  then wall time, then the same on one real constrained device (peak
  RAM, flash size, latency, energy).
- Report against **both** baselines: A (what people actually run), and
  B (is the win real beyond PyTorch's own ragged support).

The point is not "Tensora supports ragged, PyTorch does not." It is:
Tensora statically proves a ragged contract across a custom region, uses
that proof to select or generate a ragged implementation, and beats the
fallback PyTorch actually takes for that region.

**Honest risk.** For regions PyTorch already handles well (Baseline B),
the win may be small or zero. The defensible niche is custom fused
regions where PyTorch falls back to padding. This is a hypothesis to
test, not a result to assume.

**Edge-device claim needs real hardware.** "PyTorch runs out of memory
before Tensora, on a laptop" is a compiler-side result. An edge-device
claim needs the four numbers above, measured on a real device.

**Demo model.** Use a real, small, pretrained LLM and a real batch with
real skew (a few long inputs, many short). Not a toy model, not a
synthetic batch.

## 4. Data types

- **Needed:** an integer type, for `gather` (token IDs are whole
  numbers). Already part of Group B.
- **Consider later:** a smaller float or int type (fp16, bf16, int8).
  f32 is correct but the largest common inference type. Most real
  memory-limited deployments use a smaller type. This is a second lever
  for the same memory goal. Not in V0.2; a future decision.

## 5. Training (not a V0.2 goal)

Tensora is inference-only. If training is added later, the custom op
needs a real backward pass, or must stay non-differentiable so autograd
does not break. See
[roadmap doc §9.3a](11_OPEN_SOURCE_AND_RESEARCH_ROADMAP.md#93a-the-tensor-abi-boundary-granularity-and-ownership).
Listed so it is not forgotten.
