# V0.2 Closeout: Spikes and Honest Lessons

V0.2 was scoped small on purpose: not a build, but a set of spikes that
quick-check whether any future direction gives a real-world benefit
worth open-sourcing. This doc closes V0.2 with the results and the
decision.

The spike code and full numbers are in
[`research/ragged_spike/`](../../research/ragged_spike/README.md).

## What was spiked (all runnable, on an RTX 500 Ada 4 GB laptop GPU)

1. **Ragged attention** (`spike.py`) — padded vs PyTorch's own ragged
   path (`torch.nested`) vs a per-sequence loop.
2. **Ragged fused region** (`fused_spike.py`) — a whole custom region
   (attention → RMSNorm → Linear → GELU → Linear → residual): does
   PyTorch's ragged path break on it?
3. **Heterogeneity sweep** (`hetero_sweep.py`) — how the ragged gain
   tracks how uneven the batch is.
4. **Scheduling headroom** (`sched_spike.py`) — how close
   `torch.compile` (Inductor) is to the memory-bandwidth limit for
   pointwise, reduction, and fused kernels.
5. **Sharding communication** (`shard_analysis.py`, analytical) — does a
   semantic fact decide communication-free vs communication-heavy
   distribution?

## Lessons (honest)

- **Ragged is a real win, ~10-14x memory and ~8x speed** on a skewed
  batch. On the 4 GB GPU, padded attention runs out of memory where
  ragged fits.
- **But PyTorch already delivers it.** `torch.nested` handled every
  case, including the whole fused region and ragged pooling. For
  mainstream inference, a Tensora ragged pass adds nothing.
- **The ragged gain is regime-bound.** It only appears when sequence
  lengths are uneven (0% work eliminated when uniform).
- **Inductor is already at the hardware limit single-node.**
  `torch.compile` reached 89-100% of the memory-bandwidth ceiling. A
  semantic scheduler cannot beat it on one GPU.
- **The one un-dominated direction is distributed.** A semantic fact
  (batch independent vs hidden reduction) decides whether a sharding
  needs zero communication or hundreds of MB per step. But this is
  distributed, needs a cluster, and is research.
- **Verification is un-dominated too, but it is a checker, not a
  speedup.** Static named-axis / contract checking is something PyTorch
  does not do. V0.1's semantic analyzer already demonstrates this (see
  `demos/03_semantic_demo.sh`, which rejects an axis-name mismatch).

## Decision

- **On a single node, there is no runtime perf/memory win to open-source
  that PyTorch does not already deliver.** Do not open-source on a
  "faster than PyTorch" claim; the numbers do not support it.
- **Open-source V0.1 as an academic teaching compiler.** That is its
  real, defensible value.
- **Take the distributed and verification directions, and the other
  semantic-axis directions, to the professor as future research.** See
  [15_FUTURE_RESEARCH_DIRECTIONS.md](15_FUTURE_RESEARCH_DIRECTIONS.md).

## Status

V0.2 is closed. The deliverable is the spike set plus these lessons, not
a shipped feature. This is the intended outcome of a "spike the future
directions" phase: a real, evidence-based answer, including the honest
negative results.
